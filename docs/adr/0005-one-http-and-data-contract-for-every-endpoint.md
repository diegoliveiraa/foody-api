# ADR-0005 — One HTTP and data contract for every endpoint

- **Status:** Accepted
- **Date:** 2026-10-16
- **Decided by:** Diego

## Context — why this became a decision

Every endpoint answers errors, lists, dates, identifiers and amounts. Left to each endpoint, each
picks its own shape — while the front has one request-error extractor and shared list components
(foody-app R5, R4) that need exactly one. These choices are cheap before the first endpoint and
expensive after the tenth.

## Decision

- **Errors:** RFC 9457 Problem Details (`application/problem+json`) from `GlobalExceptionHandler`:
  `status`, `title`, `detail` (pt-BR, from the catalog), `instance`, plus `code` — the `Messages`
  key, stable for clients — and, on validation, `errors: [{ field, message }]`. Domain exceptions
  extend `InvalidRequestException` (400), `NotFoundException` (404), `ConflictException` (409) or
  `BusinessRuleException` (422). An unexpected error answers 500 with a generic text and is
  logged; its message never reaches the client.
- **Pagination is server-side.** A list endpoint takes `page` (from 1), `pageSize` (10, 25, 50 or
  100 — default 10, anything else is a 400) and `sort=property,asc|desc` limited to that
  endpoint's allowlist, and answers
  `{ "data": [...], "meta": { "page", "pageSize", "totalItems", "totalPages", "hasNext", "hasPrevious" } }`.
- **Dates:** instants in UTC — `Instant` in Java, `timestamptz` in PostgreSQL, ISO-8601 in JSON.
- **Identifiers:** UUID v7, generated by Hibernate.
- **Money:** `numeric(12,2)` in PostgreSQL, `BigDecimal` in Java, a JSON number in BRL — never
  `double` or `float`. Arithmetic on money happens in the API.
- **Every entity extends `BaseEntity`:** `id`, `createdAt`, `updatedAt`, `version` (optimistic
  locking, answered as 409) and soft delete — `delete()` stamps `deleted_at`, and every JPA query
  leaves deleted rows out (Hibernate `@SoftDelete(strategy = TIMESTAMP)`).
- Messages are pt-BR under a fixed locale, Bean Validation's included.

## Why this one and not the others

| Alternative | Why not |
|---|---|
| Spring's default error body or an ad-hoc `{ message }` | A shape per endpoint and no stable code to branch on |
| Spring Data's `Page` JSON (`content`, `pageable`, …) | Leaks internal structure that changes between versions |
| Cursor pagination | Right for infinite feeds, not for numbered tables; revisit for a feed |
| Any page size, silently capped | Arbitrary sizes defeat caching and invite huge pages; the UI offers four options |
| Sequential `bigint` ids | Enumerable in URLs and only known after the insert |
| UUID v4 | Random order fragments the primary-key index |
| Money as integer cents | Equally valid; decimal keeps the database readable in domain units |
| A `deletedAt` attribute filtered by hand | Every query has to remember the filter; Hibernate applies it everywhere |

## Pros

- Clients handle one error shape and branch on `code`, never on `detail` text.
- Every list screen reuses the same pagination component and the same `meta`.
- The sort allowlist stops clients from ordering by sensitive or unindexed columns.
- Deleted data stays recoverable and auditable.

## Cons

- Soft-deleted rows stay in the table: unique constraints must be partial
  (`… WHERE deleted_at IS NULL`), or a deleted row blocks creating it again.
- Deleted rows are invisible to JPA; listing or restoring them needs native SQL.
- `deleted_at` is a Hibernate-managed column, not an entity attribute.
- The page-size options live in both repos and must change together.
- `pageSize` is checked by an interceptor before any controller, on every endpoint that has it.
- JavaScript parses JSON numbers as floats: the front displays amounts and never computes them.
